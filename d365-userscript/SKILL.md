# D365 脚本制作方法

这些脚本给业务用户在 D365 页面上直接使用，操作的是正式环境的真实单据，用的人不看代码。方法围绕四条原则，后面每一步都是它们的展开：

- **系统自己的按钮是规则来源。** 脚本要做的事，页面上通常已有按钮在做。读懂按钮背后的代码，照着做，不要自己发明流程。
- **查实，不猜。** 结果里不写「可能是 A 或 B」：脚本要查清楚，直接给结论和原因。规则从代码读出来之后，再用真实数据验证。
- **先只读，后写入。** 调查阶段不写数据；第一版只预览；写入要人工确认；第一次写入只动一张单。
- **如实汇报。** 区分「在真实页面跑过」「用模拟数据测过」「没测过」，后者要明确告诉用户去试什么。

## 从哪一步开始

| 情况 | 从哪开始 |
|---|---|
| 新脚本 | 第 1 步 |
| 给已有脚本加功能、改规则 | 先读该脚本和 README 对应段落，涉及新字段或新规则时走第 2 步，然后第 4 步 |
| 用户反馈结果不对 | 先查这张单的真实数据和用户实际运行的版本，找到根因再改，不要按症状打补丁 |
| 用户说「提交并发布」 | 第 6 步 |
| 一次性查询 | 用现有脚本的同款查询在浏览器里跑，直接给结果，不用做脚本 |

新脚本动手前，先看脚本仓库里有没有能扩展的脚本。需求和现有脚本同一业务时，加功能比新开脚本好。

## 1. 明确需求，进入环境

用 **Claude in Chrome**（用户的真实 Chrome，已登录 D365），独立的浏览器通常没有登录态。自己新开一个标签页操作，不要动用户开着的页面；结束后关掉，并清理留在 `window` 上的临时变量。

先确认操作的是正式环境还是 UAT。用户说不清流程时，让其在 Chrome 打开目标页面或发截图，一般就够了。

## 2. 只读调查

用 `javascript_tool` 在 D365 标签页里直接调 Web API，代码片段见 [references/recon.md](references/recon.md)。这一步只发 GET；能读出来的就不要靠点页面。

动手写之前要有这些答案：

1. **实体和字段**：实体集名、字段逻辑名、选项值，全部从元数据查，不靠猜。名字相近的实体和字段很多，要用真实记录确认。
2. **列表范围**：取系统视图的 `fetchxml`，沿用它的过滤条件，这样脚本读到的和用户在页面看到的一致。
3. **按钮逻辑**：找到按钮对应的 Web Resource，读清它调什么接口、传什么、提交前校验什么。
4. **服务器端行为**：写入后有没有插件带出字段或算金额（查 `sdkmessageprocessingsteps`，对比刚建的记录）。
5. **数据和权限**：数据量多大、当前账号读不读得到。范围太大时要和用户商量缩小（如按业务部门 + 年份）。
6. **规则验证**：反推出的规则用真实数据全量对照，全部吻合才算；默认值从历史数据统计，并把依据告诉用户。

字段实际有没有在用也要看数据：元数据里有的字段可能全是空的，真正有值的是另一个相近的字段。

把查实的实体、字段、接口记到 `references/domain.md`（格式见 [references/domain-template.md](references/domain-template.md)），下次可以省掉重复调查。这个文件含组织内部信息，不要放进公开仓库。写入前仍要再核对。

## 3. 把方案讲给用户

用业务语言说清楚：读哪些单、分几类、每类怎么处理、会写什么。用户的说法和数据对不上时，把证据摆出来并给建议，由用户决定。

**分版本交付**，这样每一步用户都能先核对：

1. 只读预览版：列出每张单会怎么处理、为什么。
2. 用户确认预览正确后，加写入。
3. 用户挑一张真实单据实测，把结果发回来。
4. 没问题再放开批量。

## 4. 写脚本

从 [assets/template.user.js](assets/template.user.js) 开始，它已经包含下面大部分约定。单文件，不依赖构建。

**形态**：`@noframes`、`@grant none`、`@match` 写自己的 D365 域名；右下角一个悬浮按钮（`bottom` 避开其他脚本的按钮），点开面板；`@version` 从 `0.1.0` 或 `1.0.0` 起。

**读取**

- 优先走 Web API，别模拟点击：稳定、快，不受页面加载影响。
- 用 `Prefer: odata.include-annotations="*"` 拿显示值（`fmt(o, field)`）。
- 分页：`$filter` 查询跟 `@odata.nextLink`；FetchXML 用 `page` 参数和 `morerecords`。
- 按 ID 批量查时分块（每块 40 个以内，防止 URL 过长），并发 4。
- 遇到 429/503 按 `Retry-After` 重试。

**写入**，错了影响真实业务，所以每一条都有用：

- 写之前重新读一次并重新检查，因为预览之后单据可能已被别人改过。
- 创建前查是否已存在，防止重复。
- `PATCH` 带 `If-Match: <etag>`，不覆盖别人刚做的修改。
- 按钮背后是自定义 API 时就调同一个 API，不要直接改表绕过它。
- 弹 `confirm` 列出每张单的单号、金额和要做的事，不只是一个数量。
- 逐张执行，不并发；**出错就停**，把原因写到该行。
- 写完读回来，确认状态真的变了再标成功。
- 第一次高风险操作只处理一张：用 `localStorage` 记这台电脑是否验证过（模板的 `VERIFIED_KEY`）。
- 多步操作中途失败时，写清停在哪一步、单子现在什么状态、谁来接手。写操作结果不明时不自动重试，交给人工核对。

**页面校验要自己补。** 接口不等于页面：必填校验常常只写在表单脚本里，接口放行，字段空着也能提交。把按钮里的校验逐条搬进预检查，分成「拦住」和「只提醒」，分类依据是页面实际行为，不是配置值。

**结果展示**

- 按类别分组，可折叠，整组勾选，可处理的排前面；已完成的默认收起。
- 最后一列写结论和具体原因，颜色区分：绿通过、黄提醒、红拦住。原因要细到哪一项、实际多少、应该多少。
- 单号做成链接，新标签页打开，`appid` 取当前 URL。
- 提供「复制表格」（TSV，直接粘 Excel）；单号按文本处理，防止变成科学计数法。
- 提供「停止」按钮；提供一键勾选这类操作时，确认框仍然保留。

**密钥**不写进脚本（脚本会进 git 和 Gist）。需要 API Key 时让用户在面板里填，用 `GM_setValue` 保存。

开始写之前，扫一眼 [references/pitfalls.md](references/pitfalls.md)，里面都是实际开发中遇到的问题。

## 5. 验证

1. `node --check 脚本.user.js`。
2. 把完整脚本注入**自己开的** D365 标签页，用真实数据点「读取 / 预览」，对照页面核实结果。注入方法见 recon.md（本地 HTTP 服务会被 Chrome 的本地网络限制挡住）。
3. 写入逻辑**不在正式数据上试**：拦截 `window.fetch`，让写接口返回模拟的成功和失败，确认取消确认时不发请求、失败时会停下、结果显示正确。
4. 真实写入由用户挑一张单来测。

## 6. 发布（用户要求时才做）

用户说「提交并发布」时：

1. 升 `@version`：修问题加第三位，新功能加第二位。ScriptCat 只有在版本号变大时才更新。
2. 更新 README 里该脚本的段落，单独提交。
3. 提交并推送脚本，提交信息用 `<脚本简称> <版本>：<改了什么>`。
4. 把脚本同步到 Gist（`gh api -X PATCH gists/<GIST_ID>`，文件内容用 `jq --rawfile` 组装），再读回确认是新版本。发布被权限拦下时，把命令给用户自己运行，并说明现在停在哪一步。

**新脚本第一次接入在线更新**：

- 头部加 `@updateURL` 和 `@downloadURL`，指向私密 Gist 里的英文文件名。
- 告诉用户：先在 ScriptCat 删掉手动粘贴的旧版，再打开 raw 地址安装，否则两份会同时运行；GitHub 的 raw 地址有几分钟缓存。

## 7. 汇报

用业务语言，先说结论：能用了吗、怎么用、规则是什么。规则要给依据（读了哪个按钮的代码、对照了多少数据）。最后说清哪些没测过、用户第一次用时要看什么。如果发现了用户没问但会影响结果的问题（比如流程漏洞、历史数据问题），一并说明。
